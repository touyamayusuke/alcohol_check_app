# 03. 設計

`02-要件.md` で決めたものを、**どう作るか**に落とします。

いちばん大事なのは「持つデータ」です。
画面はあとから何度でも変えられますが、データの持ち方を途中で変えるのは高くつきます。

---

## 持つデータ

> 何を、どういう単位で保存するか。日本語で書いてかまいません。
>
> 迷ったら、こう考えます。**「今の状態」を欄に書くのか、
> それとも「できごと」という別のものを作って積み上げるのか。** どちらでも動きます。違うのは、あとでできることです。

- 「社員 — 内部ID（自動採番）、社員番号、名前、パスワード、権限（一般社員／管理者）。開発時点で4人ぶん」
- 「アルコールチェック — 内部ID（自動採番）、実施者（社員への参照）、区分（出社時／帰社前）、測定値、確認者（社員への参照）、検知器を使用したか、登録日時」

社員の「今日の状態」は社員の欄には持たせない。アルコールチェックを、実施のたびに1件ずつ積み上げる方式にする。
その日・その区分の記録があるかどうかは、あとでアルコールチェックを検索して判定する（「処理の流れ」に記載）。

### ID と社員番号の使い分け

- ログイン時に人が入力するのは社員番号。それ以外の画面・パラメータでは、すべて内部ID（社員テーブルの主キー）で社員を指す。
  例：アルコールチェックの確認者、社員一覧の `data-user-id`、チェック一覧の `data-check-id`。
- 社員番号は人が読み書きするための識別子、内部IDはシステム内部が参照するための識別子、と役割を分ける。
- 画面には常に名前を表示し、社員番号・内部IDはどちらもログイン画面の入力欄以外では表に出さない。

## 画面

> どの画面に何を出すか。`01-要求.md` のアドレスと目印を守ってください。

画面のアドレス・送る項目・目印は `01-要求.md` の「画面・操作一覧」「画面につける目印」の通り。
ここでは、それぞれのパラメータが上の「持つデータ」のどこに対応するかだけ補足する。

| `01-要求.md` のパラメータ・目印 | 対応する持ち方 |
|---|---|
| `employee_number` | 社員．社員番号（ログイン画面でのみ使う） |
| `checker_id` | アルコールチェック．確認者（社員への参照、内部ID） |
| `data-check-id` | アルコールチェック．内部ID |
| `data-user-id` | 社員．内部ID |
| `check_type` | アルコールチェック．区分 |
| `alcohol_value` | アルコールチェック．測定値 |
| `used_detector` | アルコールチェック．検知器を使用したか |
| `role` | 社員．権限 |

## 処理の流れ

> 「登録」を押してから画面が変わるまでに、何が起きるか。
> とくに、**すでにその区分を登録済みのときに登録しようとしたら何が起きるか**、
> **自分自身を確認者に選ぼうとしたら何が起きるか**を書いてください。

1. 実施者が、測定値・確認者・検知器使用のチェックボックスを入力して登録ボタンを押す。
2. サーバは、ログイン中の社員が「今日」「その区分」のアルコールチェックをすでに持っているかを調べる。
   - すでにあれば、登録せずにエラーを出して登録画面に戻す（二重登録を防ぐ）。
3. 確認者にログイン中の社員自身が選ばれていないかを調べる。
   - 自分自身であれば、登録せずにエラーを出して登録画面に戻す（自己確認を防ぐ）。
4. どちらも問題なければ、アルコールチェックを1件作成する（実施者・区分・測定値・確認者・検知器使用の有無・登録日時）。
5. 登録画面に戻る。その区分は、入力フォームの代わりに登録済みの内容を表示する状態に変わる。

管理者の社員一覧を開いたときは、社員ごとに「今日・出社時のアルコールチェックがあるか」「今日・帰社前のアルコールチェックがあるか」を調べ、なければ「未実施」、あれば実施済み（測定値）として表示する。

## そう決めた理由

> 「なぜその持ち方にしたのか」を、ひとことずつ添えてください。

- **社員に「今日の状態」を持たせず、アルコールチェックを都度積み上げる方式にした。**
  過去の記録をそのまま履歴として使え、「未実施」の判定も「今日・その区分の記録があるか」を検索するだけで済むため。
  社員側に状態を持たせると、記録との二重管理になり、あとから履歴も追えなくなる。
- **確認者・実施者を、名前や社員番号ではなく内部IDへの参照にした。**
  名前は同姓同名がありえて社員を一意に指せず、社員番号も将来変わりうる。内部IDは変わらないので、
  表示名や社員番号があとで変わっても過去記録の指し先がずれない。
- **検知器使用の有無を、都度記録するチェックボックス（デフォルトON）にした。**
  対面かどうかは確認者を選ぶ設計そのものが保証してくれるが、検知器を実際に使ったかどうかは実施者側の
  当日の状況に依存し、仕組みでは保証できない。フィールド自体を持たず「常に使用した」と固定してしまうと、
  検知器が使えなかった日の記録が事実と異なってしまい、法令が求める「実際の確認方法の記録」に反する。
  デフォルトONのチェックボックスなら、通常運用では操作コストがかからず、例外の日だけ正しく記録できる。
- **対面／非対面を区別する列は持たない。**
  確認者は「その場にいる社員」から選ぶ設計そのものが対面を強制しており、非対面のフローはそもそも
  作らないと決めた（`02-要件.md`）ため、区別する必要がない。

## Claude Code に聞くなら

書き終えたら、こう渡します。

```
docs/03-設計.md を書きました。
この持ち方だと、あとから困りそうなことを3つ挙げてください。
別の持ち方があるなら、それも1つ示してください。どちらが良いかは、まだ言わなくて結構です。
まだ実装はしないでください。
```

## 実装させたあとに、必ずやること

Claude Code に実装させると、`db/schema.rb` というファイルができます。
**これが、あなたの設計が実装に着地した姿です。**

この文書の「持つデータ」と `db/schema.rb` を並べて読んでください。

- 書いたつもりのないカラムが増えていませんか
- 書いたはずのものが落ちていませんか
- 名前は、あなたが読んで意味が分かるものになっていますか

違っていたら、**実装ではなく、まずこの文書を直します。**
決めたことと動いているものが食い違ったまま進むと、あとで誰も理由を説明できなくなります。
