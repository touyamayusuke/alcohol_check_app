# アプリ専用コードレビュー

このリポジトリ（社内アルコールチェック記録アプリ）の**ユーザーが指定したファイル**をレビューし、日本語で重要度別レポートを返すスキル。

一般的なRailsの指摘よりも、**このアプリ固有の業務ルールと権限制御が壊れていないか**、**プロジェクト規約に沿っているか**を重視する。アルコールチェックは法令対応の記録なので、二重登録や権限すり抜けは「見た目の問題」ではなく実害につながる。レビューの価値はそこを確実に拾えるかで決まる。

## 手順

### 1. 対象ファイルを確定する

- ユーザーが指定したファイル（またはディレクトリ配下のファイル）を対象にする。
- 指定がなければ推測で広げず、どのファイルを見るか聞く。
- 対象ファイルは部分ではなく全体を読む。

### 2. 判断基準となるドキュメントを読む

以下を毎回読む。ルールは更新されうるので、このスキルに書かれた要約より**ファイルの現在の内容を正**とする。

- `CLAUDE.md` — 業務ルール、コントローラー構成、権限制御の設計意図
- `.claude/rules/coding.md` — コーディング規約
- 詳しい観点リストは `references/checklist.md` を参照

ドキュメントと実コードが食い違っていたら（例: ドキュメントでは各コントローラーに `require_admin` があると書かれているが、実際は `Admin::BaseController` に共通化済み）、実コードを優先して判断する。そのうえでドキュメントを更新すべき点として🟢で触れる。

### 3. 関連ファイルを読む

業務ルールは複数レイヤーにまたがるので、対象ファイル単体では正しく判断できない。対象に応じて次を読む。

| 対象 | 合わせて読むもの |
|---|---|
| モデル | `db/schema.rb`（制約・インデックス）、対応する `test/models/*_test.rb` |
| コントローラー | `config/routes.rb`、親クラス（`Admin::BaseController` 等）、対応するテスト（`test/controllers/`, `test/integration/`） |
| ビュー | それを描画するコントローラー |
| マイグレーション | `db/schema.rb`、関連モデルのバリデーション |
| テスト | テスト対象のコードと `test/fixtures/*.yml` |

### 4. Rubocopを実行する

```sh
bin/rubocop <対象ファイル>
```

機械的なスタイル（クォート、スペース等）はRubocopに任せ、目視で細かく拾い直さない。違反があれば件数と代表例をレポートにまとめる。実行できない環境なら、その旨をレポートに書く。

### 5. レビューする

`references/checklist.md` の観点で確認する。特に以下は見落とすと実害が出るので必ず確認する。

- **二重登録防止**: `user_id + check_type + checked_on` の一意性が、モデルのバリデーションとDBのユニークインデックスの**両方**で一貫しているか。片方だけの変更、条件のずれ（例: 片方は `checked_on`、片方は `Date.current` を見ている）がないか。
- **確認者は本人不可**: `checker_id == user_id` を防ぐロジックが保たれているか。
- **権限制御**: admin 名前空間のコントローラーが `Admin::BaseController` を継承する（あるいは `require_admin` を通る）か。ビューでリンクを隠すだけで済ませていないか。一般ユーザー向けアクションで `current_user` 以外のレコードを操作できる経路がないか。
- **Strong Parameters**: `user_id`、`role`、`checked_on` など、ユーザーが自由に変えてはいけない属性を permit していないか。

指摘は「なぜ問題か」を業務上の影響で説明する。例えば「`role` を permit している」だけでなく「一般ユーザーが自分を admin に昇格できる」まで書く。影響を書けない指摘は、たいてい重要度が低い。

### 6. レポートを出力する

下のフォーマットで出す。

## 重要度の基準

- **🔴 必須**: 業務ルール違反、権限のすり抜け、データ不整合、例外や誤動作を起こすバグ。マージ前に直すべきもの。
- **🟡 推奨**: `coding.md` の規約違反、業務ルールに対するテスト不足（正常系/異常系ペアの欠落、モデルと統合テストの片方しかない等）、N+1、重複コード。
- **🟢 提案**: 可読性、命名、ドキュメントの更新、将来の保守性。

既存コードに以前から残っている規約違反は🟢にとどめる。新規・変更部分の違反と同じ重さで扱うと、レポートがノイズで埋まるため。

根拠が弱く「もしかしたら」程度の指摘は出さないか、🟢に「要確認」として書く。確度の低い🔴は信頼を損なう。

## 出力フォーマット

```markdown
# コードレビュー: <対象ファイル>

## 概要
<2〜3文。ファイルの役割と、全体として問題があるかどうか>

## 🔴 必須
### 1. <指摘タイトル>（`path/to/file.rb:行番号`）
- **問題**: <何が起きているか>
- **影響**: <業務上/セキュリティ上どう困るか>
- **修正案**:
  ```ruby
  <修正後のコード>
  ```

## 🟡 推奨
### 1. ...（同じ形式）

## 🟢 提案
- <1〜2行の箇条書きでよい>

## 良い点
- <規約や設計意図に沿っている点を1〜3個。なければ省略>

## 確認したこと
- 読んだ関連ファイル: <一覧>
- Rubocop: <結果の要約。例「違反なし」「3件（Style/StringLiterals ×3）」>
```

該当する指摘がない重要度のセクションは「なし」と書く（セクションを消すと、確認したのか忘れたのか区別できないため）。

修正は提案にとどめ、ユーザーから頼まれるまでファイルを編集しない。
